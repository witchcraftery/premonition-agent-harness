01 / ROOT DIAGNOSIS

Why LLMs Live Only in the Present

What the FLARE paper reveals, and why it validates the concept you've intuited.

The paper establishes a crisp, formal distinction: reasoning ≠ planning. Every standard LLM reasoning technique — chain-of-thought, beam search, ReAct, Reflexion — operates as a step-wise greedy policy. At each moment, it selects the locally highest-scoring next action. It has no mechanism to propagate backward from future consequences. The result is what they call myopic commitment: early decisions that look correct moment-by-moment, but lock in trajectories that collapse over longer horizons.

Your intuition, formally proven

Proposition 3.1 (FLARE paper): A step-wise greedy policy can be forced into zero return while an optimal trajectory with unbounded return exists — just by placing the reward beyond the current moment. The suboptimality gap is arbitrarily large. The LLM can't know what it doesn't simulate forward.

Their solution, FLARE, uses Monte Carlo Tree Search (MCTS) with three minimal requirements: (1) explicit lookahead — simulate future trajectories before committing; (2) backward value propagation — let downstream outcomes revise early decisions; (3) receding-horizon commitment — only commit to the next action, then replan. This is the theoretical backbone your architecture needs to formalize.

Key distinction for your architecture

FLARE is still a single model doing sequential lookahead. What you're proposing goes further: a parallel swarm that isn't answering the current question at all — it's pre-simulating the next environment states while the face model handles now. This is the leap from FLARE to a precognitive architecture.

02 / CORE ARCHITECTURE

The Three-Layer Brain

Face Model · Swarm Brain · Probability Engine — each with a distinct temporal focus.

// Temporal layers of cognition

Layer 1 · NOW

Face Model

The user-facing agent. Speaks, responds, acts. Optimized for fluency and delivery.

  • Receives present-state context
  • Pulls pre-solved answers from Swarm cache
  • Delivers output without internal debate
  • Streams responses while Swarm runs ahead
  • Lightweight — fast inference, smaller model

Layer 2 · NEAR FUTURE (+1/2/3 steps)

Swarm Brain

Parallel agent cluster. Not answering questions — predicting what questions come next.

  • Spawns N simulation branches per tick
  • Each agent tests a probability hypothesis
  • Runs MCTS-style forward rollouts
  • Scores branches via trajectory-level value
  • Feeds winning paths to Face cache

Layer 3 · POSSIBILITY SPACE

MiroFish Engine

Probability simulation universe. Generates, tests, and ranks the tree of possible next realities.

  • Maintains a live probability tree of env states
  • Samples agent behaviors from distribution
  • Scores paths by likelihood × utility
  • Prunes dead branches automatically
  • Provides swarm with pre-ranked hypotheses

// data flow · real-time loop

MiroFish → ranked probability tree of next N states → Swarm → pre-solved responses per branch → Face
Face → actual event happens, state captured → MiroFish → prune tree, advance horizon, recompute

The Core Insight

The face model is never deliberating — it's executing from a pre-computed cache. The deliberation happened in the background, asynchronously, while the last response was being delivered. The latency budget is spent on prediction, not reaction. This is the opposite of how every current agent works.

03 / MIROFISH INTEGRATION

Why MiroFish Fits This Role

What the MiroFish repository offers as a probability engine substrate.

MiroFish is an agent swarm "universe" — a simulation sandbox where agents run, interact, and generate probability distributions over outcomes. Its architecture (Node.js backend, containerized via Docker) is designed for running parallel agent scenarios. This maps almost directly to what you need, with some intentional re-framing of what the agents are optimizing for.

MiroFish Native Capability Role in Thought Harness Required Extension
Parallel agent spawning Swarm branch generation Add scoring/ranking layer per branch
Probability tracking per scenario Next-state distribution Connect to real environment event stream
Universe state management Possibility tree persistence Add TTL pruning + horizon advancement
Agent communication bus Swarm → Face cache push API endpoint for Face model to query cache
Simulation replay Post-hoc accuracy analysis Minimal — already built in

Key reframe needed

MiroFish agents currently simulate what other agents do. Your use case asks them to simulate what the external user/world does. This is a different target distribution — you're modeling the environment's next move, not just the agent's. The agents need to become world-simulators, not just agent-simulators. This is achievable with prompt-level framing and a context feed from the Face layer.

04 / RUNTIME LOOP

The Receding-Horizon Thought Loop

How the system runs in continuous, overlapping asynchronous cycles.

// Pseudocode: Precognitive Agent Loop
// Three concurrent processes, loosely synchronized

async FACE_LOOP(env_stream, swarm_cache):
  while active:
    event = await env_stream.next()           // user says something / action occurs

    // Check if swarm already solved this
    match = swarm_cache.lookup(event)

    if match.confidence > THRESHOLD:
      response = match.pre_solved_response      // deliver without thinking
    else:
      response = face_model.generate(event)     // fallback: think now

    yield response
    swarm.update_ground_truth(event)            // tell swarm what actually happened

async SWARM_LOOP(prob_engine, face_cache):
  while active:
    top_branches = prob_engine.get_top_k(k=5)  // get 5 most likely next realities

    for branch in top_branches:
      agent = spawn_agent(branch.hypothesis)
      response = agent.pre_solve(branch.context)
      face_cache.store(branch.event_signature, response, branch.probability)

    await sleep(100ms)                         // continuous background cycle

async PROB_ENGINE_LOOP(env_history, mirofish):
  while active:
    new_event = await swarm.get_ground_truth()

    mirofish.prune_tree(new_event)              // eliminate paths that didn't happen
    mirofish.advance_horizon(new_event)         // shift lookahead window forward
    mirofish.expand_branches(depth=3)         // grow new possibility branches

    // Score all branches: P(next_event) * utility(response)
    mirofish.score_and_rank()

The key insight from FLARE's receding-horizon design applies here directly: never commit long-term. The prob engine advances one step at a time, using actual events to prune impossible futures. This prevents the "brittle long-term commitment" failure mode the paper identifies in offline planners.

05 / BUILD PLAN

Four-Phase Implementation

From minimal proof-of-concept to full precognitive harness.

  • 01

    The Skeleton: Face + Cache Interface

    Build the Face model as a thin wrapper that checks a cache before generating. The cache is initially empty. Instrument every response with: what event triggered it, what was returned, and latency. This creates the ground-truth data pipeline for training the prob engine. Stack: Python/FastAPI, async Redis for cache, any small-but-sharp LLM (Qwen2.5-7B or similar locally on MLX).

  • 02

    The Swarm: Parallel Branch Agents

    Deploy a small swarm (3–5 agents) using MiroFish as the parallel execution substrate. Each agent takes a hypothesis about the next likely user action and pre-generates a response. Use prompt-level world-modeling: "Given the conversation so far, the user is likely to next ask about X. Pre-generate the ideal response to X." Measure cache hit rate vs. baseline. Target: 40%+ cache hit within first 50 interactions.

  • 03

    The Probability Engine: MiroFish + Scoring

    Extend MiroFish's agent universe with a scoring layer: each simulated branch gets a probability score (based on pattern matching against historical event sequences) and a utility score (how complete/useful is the pre-solved response). Implement MCTS-style backward value propagation — when a branch's prediction was correct, increase the weight of the pattern that generated it. This is the learning loop. Key metric: prediction accuracy over 1, 2, and 3 steps ahead.

  • 04

    The Harness: Full Integration + Latency Orchestration

    Wire all three layers with proper async orchestration. The Face streams output while the Swarm is already 1-3 steps ahead. Tune the confidence threshold for cache use vs. live generation. Add a "moment capture" layer that records the exact state of the environment at each tick — conversation context, tool states, external data signals — so the prob engine has rich features to model. Evaluate: perceived latency, response quality, and prediction accuracy as a compound metric.

07 / OPEN QUESTIONS

Where This Gets Hard

The genuine challenges that will shape how you build and iterate.

Event Signature Design

How do you represent "what just happened" in a way that's both specific enough to look up and fuzzy enough to match approximate situations? Embedding-based lookup is the answer, but tuning the similarity threshold is an empirical problem. Too strict: low hit rate. Too loose: wrong pre-solved responses get delivered.

Prediction vs. Creativity

For novel, creative, or deeply context-dependent queries, the probability engine may not generate useful branches. The face model's live fallback needs to be strong. The system should gracefully degrade — cache miss isn't a failure, it's just slower.

Compute Budget on Local Hardware

Running 3 Face + 5 Swarm agents + prob engine concurrently on a Mac Studio is feasible with quantized models, but you'll need to profile memory bandwidth carefully. Recommend: Face at 4-bit quant, Swarm agents at 4–8 bit, prob engine as a pure Python statistical module (no LLM needed for the scoring/ranking).

The FLARE Warning

FLARE's paper notes that as it reduces myopic commitment, residual failures shift to looping and premature termination — not wrong early choices, but inadequate exploration coverage. Your swarm will face the same: the branches it doesn't generate are the dangerous ones. Build diversity metrics into your branch generation — reward the swarm for exploring low-probability but high-impact paths, not just the most likely next move.
