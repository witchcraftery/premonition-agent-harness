System concept · one-page architecture overview

Predictive Agent Harness

A two-layer agent system that responds in the present while quietly preparing for the most likely near-future events. Instead of forcing one LLM to both talk and foresee, the ecosystem separates present-time delivery from background possibility projection.

Core premise
Do not make the speaking model predict everything.

Let the front agent stay grounded, coherent, and fast. Let a background swarm model the next one to three likely events, precompute support, and hand only useful preparation forward.

Working name
Predictive receding-horizon agent loop

Not full “precognition,” but a disciplined system for shallow lookahead, branch scoring, and continuous replanning as reality updates.

Operating thesis
observe → hypothesize next events → simulate shallow branches → score utility of preparation → front agent acts → replan on new evidence
Fast front agent Background branch engine Optional swarm simulation
Why this architecture exists

Reasoning is not the same thing as planning, and planning is not the same thing as forecasting

The pressure on a single LLM
  • Answer correctly in the moment
  • Stay conversational and on-brand
  • Track tasks, context, and constraints
  • Anticipate blockers and user shifts
  • Prepare for what happens next
The proposed release valve
  • Front agent handles what is true now
  • Prediction layer handles what may happen next
  • Simulation layer explores second-order effects only when useful
  • Preparation is kept internal until reality confirms the branch
  • System replans after each real event instead of overcommitting

The result is a calmer public-facing intelligence and a more proactive private cognition layer.

System architecture

Five-layer ecosystem

1. State encoder

Transforms current reality into structured context: user intent, recent events, tool outputs, goals, commitments, uncertainty markers, and environment state.

2. Branch generator

Produces candidate next events, not answers. Each branch includes a hypothesis, probability, trigger signals, and why it matters.

3. Branch simulator

Explores 1 to 3 steps forward. For simple cases this is lightweight lookahead. For richer systems, a MiroFish-like swarm can simulate social or multi-actor dynamics.

4. Value propagator

Scores branches by downstream usefulness, not just plausibility. High-value branches are the ones worth preparing for before they arrive.

5. Presenter agent

The visible face. It speaks only from observed reality, while consuming prepared research, drafts, fallbacks, and next-step options from the branch engine.

6. Memory and telemetry

Stores branches, outcomes, misses, recoveries, and readiness wins so the whole loop can be tuned against reality over time.

Execution loop

How the system thinks in motion

Observe current stateGround truth only

Conversation state, live tasks, tool outputs, known constraints, unresolved uncertainties, and external signals are captured as the momentary state.

↓
Generate event candidatesNext-event prediction

Examples: user asks a follow-up, rejects the plan, accepts and wants execution, system throws an error, missing credential appears, or a stakeholder asks for status.

↓
Simulate shallow branches1–3 steps ahead

Each branch explores what follows, what evidence would confirm it, and what preparation would become valuable if it turns out to be real.

↓
Score preparation valueExpected readiness

Readiness is estimated by probability × impact × usefulness of prep, minus cost of false preparation.

↓
Prepare quietlyInternal support only

The system drafts fallback replies, command sequences, research notes, decision trees, and tool plans, but does not present them as truth yet.

↓
Front agent respondsFast and grounded

The visible model handles the present moment with less pressure, using the background work only when reality confirms a branch or when prep is safely reusable.

Optional simulation substrate

Where a MiroFish-style engine fits

Best fit
  • Complex multi-actor situations
  • Social response and public-reaction scenarios
  • Second-order consequence testing
  • Policy, messaging, or rollout rehearsals
  • Offline scenario labs for agent evaluation
Not the best fit
  • Every single chat turn
  • Low-latency assistant responses
  • Simple deterministic next-step tasks
  • Cases where a lightweight branch predictor is enough
  • Any situation where simulated narrative starts replacing observed facts

The simulation engine is best treated as a high-cost, high-richness forecasting module, not the default brain for every turn.

What this is meant to gain

Expected advantages

Less surprise

Fewer situations where the agent is caught flat-footed by common next events or predictable blockers.

Better responsiveness

Prepared research and fallback paths reduce time-to-useful-action when the next branch becomes real.

Cleaner front-agent behavior

The speaking model can stay focused on delivery, clarity, and action instead of carrying the whole future in working memory.

More graceful recovery

Because branches are shallow and continuously replanned, early mistakes do less damage than in a fully committed chain of reasoning.

The goal is not perfect prediction. The goal is higher readiness when reality arrives.
Measurement

How success could be evaluated

Prediction quality
  • Top-1 next-event accuracy
  • Top-3 branch recall
  • Calibration of branch confidence
Readiness quality
  • Time-to-useful-response reduction
  • Prepared artifact reuse rate
  • Recovery speed after branch change
User value
  • Higher helpfulness ratings
  • Lower repeated-context burden
  • More proactive resolution of blockers
readiness_score = P(branch) × impact(branch) × usefulness_of_preparation(branch) − cost_of_false_prep
Risks and guardrails

What can go wrong, and how to contain it

Risk: hallucinated futures

Branches can feel coherent without being grounded. Guardrail: keep simulation outputs internal until evidence confirms them.

Risk: simulation theater

A rich swarm can look impressive while adding little value. Guardrail: benchmark against simple baselines first.

Risk: cost explosion

Too many branches and too much simulation burn tokens and time. Guardrail: strict branch budgets and staged escalation.

Risk: premature commitment

The front agent may trust the branch engine too much. Guardrail: the presenter only speaks from observed reality and verified prep.

Recommended build path

Phased next steps

Phase 1 · Lightweight branch predictor

Predict the top three likely next events in a narrow domain, such as coding help, support chat, or task execution, and log outcomes.

Phase 2 · Quiet prep memory

Attach reusable artifacts to branches: drafts, commands, dependency checks, citations, fallback plans, and recovery scripts.

Phase 3 · Receding-horizon replanning

After every real event, collapse dead branches, rescore survivors, and cheaply regenerate the next horizon.

Phase 4 · Selective swarm simulation

Introduce MiroFish-style or multi-agent simulation only for high-uncertainty, multi-actor, or high-impact contexts.

Best first proving ground: a narrow assistant workflow where next-event accuracy, readiness gains, and recovery can be clearly measured.
